Let the small model prefill

Passing KV cache between language models

LLMs
Inference

Published

November 18, 2026

In How do we transfer context between models?, OneTriangle explore an interesting idea: a smaller model like Qwen3.5-4B can handle prefill for a bigger model. Since the smaller model needs less compute, this can save a lot of prefill time.

That got me thinking: if a smaller model can handle prefill, we could do that work with a smaller compute budget and fit in more requests. That could help boost throughput for a given amount of compute.

I wanted to see whether this idea works in practice, so I started by reproducing the recipe. From there, I tried a few different model pairs and ways of sharing the work:

  • Reproduce the recipe on a simpler Qwen model pair and see whether it works
  • Do keys or values matter more for the transferred cache?
  • Can this work with a hybrid DeltaNet model?
  • What happens if I transfer only some layers?
  • What if the big model reads the end of the prompt itself?
  • Does it hold up on long contexts?
  • Can a dense model prefill for a mixture of experts?
  • What happens across model families and tokenizers?

Before getting into those experiments, here is a quick primer on the KV cache and what gets transferred.

A quick primer on KV cache

Generating a response has two parts: prefill and decode.

During prefill, the model processes the prompt tokens. In each attention layer, it computes queries, keys and values. Each token uses its query to attend to the keys and values of the tokens it is allowed to see. The model saves the keys and values for the prompt in a KV cache, and uses the prefill output to predict the first response token.

During decode, the model generates the rest of the response one token at a time. At each step, it processes the latest token and computes its query, key and value. It uses the new query to attend to the cached keys and values from the prompt and earlier generated tokens, then adds the new key and value to the cache. That way it can use the earlier context without recomputing its keys and values at every step.

For a long prompt, prefill can take a while because the model has to process all those prompt tokens before it starts generating. A bigger model generally needs more compute for that work. The idea behind cache transfer is to let a smaller model do that reading, then use a learned mapper to turn its states into a cache the bigger model can use.

The recipe: a small model reads for a big model

OneTriangle describe this recipe in their cache-transfer post. To reproduce it, we freeze both models and train a mapper: a set of linear maps that turns the small model’s states into keys and values for the big model’s cache. We build separate maps for the keys and values of each target layer. The layer-selection method and settings below describe our implementation.

Stage 1: fit a direct map

First, we run both models on the same text and collect the keys and values their layers produce. For each big-model layer, we test how well each small-model layer can predict its keys. We use ridge regression to fit a linear map: it looks for a close match while keeping the map’s weights from becoming too large. We select the three small-model layers with the lowest prediction error, combine their outputs, and fit a new map using all three. We repeat the process separately for values.

The picture below follows one of those maps. Each block represents a layer; the counts are illustrative. The highlighted small-model layers supply the input for one big-model layer. We repeat this for every target layer to build its cache.

We can use this ridge map as it is. In the Qwen3-0.6B → Qwen3-8B reproduction below, it reaches a KL of 0.42, compared with 0.73 when the big model gets no prefix. That is a useful starting point, but there is still room to improve.

Stage 2: train a correction

Next, we improve the ridge map by adding a trainable correction: W = W₀ + A·B. The two smaller matrices A and B let us adjust the map without training a full new matrix. Their product has rank 64, and B starts at zero, so training begins with the ridge map.

We start with documents from FineWeb-Edu and tokenize them before training. We keep documents long enough for the largest split: at least 2,176 tokens. At each training step, we choose a prefix length between 512 and 2,048 tokens and sample documents from the training set. For each document, we take that many tokens from the beginning as the prefix, then take the next 128 tokens as the continuation. The prefix gives the models context, and the continuation gives us a way to compare their predictions.

The teacher is the big model processing both parts with its own cache. For the student, the small model reads the prefix and the mapper builds a cache for it; the big model then processes the continuation using that mapped cache. We compare what the teacher and student predict at each continuation position, and train the correction to bring those predictions closer using KL divergence. Both language models remain frozen.

We use AdamW at a learning rate of 2e-4, with 8 documents per step for 1,000–1,500 steps. At inference, the maps use bf16. In the same Qwen reproduction, this second stage brings KL down from 0.42 to 0.13.

Before looking at the results, let’s walk through how we evaluate each model pair.

  • Next-token distribution agreement. We give the big model a 2,048-token prefix and a 128-token continuation from each of 64 held-out FineWeb-Edu documents. We compare its next-token probability distributions when it uses the transferred prefix cache against when it builds the prefix cache itself. We report KL divergence, where lower means the distributions are closer, and top-1 agreement, where higher means the two runs more often assign the highest probability to the same token.
  • Task accuracy. We evaluate on SQuAD (300 questions, with the relevant paragraph hidden among distractors, about 4.2k tokens), HotpotQA (300 questions, with distractor documents padded to about 4.5k tokens), and GSM8K (400 questions, with eight worked examples in each prompt, about 1.1k tokens). The documents or worked examples make up the prefix whose cache we transfer. We feed the question header to the big model normally.
  • Prefill time. We measure elapsed prefill time for one request at a time and report the best of three runs, unless stated otherwise.

The early reproduction uses 128 held-out documents for fidelity; later runs use 64. The long-context experiments also have their own task settings, which we’ll cover when we get there.

Experiment 0: reproducing the recipe on Qwen3-0.6B → Qwen3-8B

We start with a simple transformer architecture that uses attention layers throughout. We choose Qwen3-0.6B as the small model and Qwen3-8B as the big model, and try the cache-transfer recipe on this pair before moving on to hybrid models.

First, we use the direct weight mapping from Stage 1 to build the 8B’s prefix KV cache. We then feed the continuation to the 8B and record its next-token probability distributions. As a reference, we run the same continuation after letting the 8B build its own prefix cache. The average KL divergence between the two runs is 0.42. For another comparison, we run the 8B on the continuation without giving it the prefix or a prefix cache. Comparing that run’s next-token distributions with the reference run, where the 8B reads the prefix itself, gives a KL of 0.73. After we train the correction in Stage 2, the KL drops to 0.13, meaning the next-token distributions are closer to those from the 8B’s own cache. This metric compares token probabilities, not the KV values directly.

Let’s look at what these results tell us.

  1. The transferred cache preserves more information for SQuAD than for the reasoning tasks. With Qwen3-0.6B doing prefill and the 8B answering, SQuAD F1 is 0.721, close to 0.738 when the 8B builds its own cache. On HotpotQA, F1 drops from 0.603 to 0.461; on GSM8K, accuracy drops from 0.925 to 0.665.
  2. We also need to compare against the small model answering on its own. For example, when Qwen3-4B does prefill and the 8B answers using its cache, GSM8K accuracy is 0.877. But the 4B answers correctly 0.915 of the time on its own. In this case, adding the mapper and the 8B does not improve the score.

We also repeat the round-3 run on a different machine using the same command. The average KL divergence between the 8B’s next-token distributions changes from 0.128 to 0.129. Task scores vary by about 0.02–0.04 between independent training runs, so we should keep that variation in mind when comparing the results below.

Experiment 1: which matters more, keys or values?

The first experiment tells us that the transferred cache changes the 8B’s next-token distributions. But the cache contains two different things: keys and values. We want to know which part contributes more to that change for Qwen3-0.6B → Qwen3-8B.

We use the rank-16 mapper trained in Experiment 0. To see how mapped keys and mapped values each affect the 8B’s next-token distributions, we run the 8B with three versions of the prefix KV cache:

  1. Keys and values mapped from 0.6B: use the mapper to build both parts of the cache.
  2. 8B keys, values mapped from 0.6B: use the keys the 8B produces when it reads the prefix, and map the values from 0.6B.
  3. Keys mapped from 0.6B, 8B values: map the keys from 0.6B, and use the values the 8B produces when it reads the prefix.

For each cache, we feed the continuation to the 8B and compare its next-token probability distributions with the distributions from the 8B reading the full prefix itself. We use 128 held-out FineWeb-Edu documents, with a 2,048-token prefix and a 128-token continuation. Lower KL divergence means the distributions are closer to the reference.

Prefix cache used by the 8B KL divergence Top-1 agreement
Keys and values mapped from 0.6B 0.135 0.842
8B keys, values mapped from 0.6B 0.134 0.844
Keys mapped from 0.6B, 8B values 0.094 0.876

Replacing the mapped keys barely changes the KL: 0.135 becomes 0.134. Replacing the mapped values brings it down to 0.094. In this test, the 8B’s own values help its next-token distributions more than its own keys do. OneTriangle reported the opposite for their model pairs, so we should not assume the same result for every pair.

Experiment 2: partial-layer transfer

The transferred cache works well on SQuAD, but the 8B loses accuracy on the reasoning tasks. This raises a question: can we recover some of that accuracy by letting the 8B process part of the prompt itself?

So far, we have transferred keys and values for every layer. This time, we let the 8B compute some layers during prefill and use mapped keys and values for the others. We can then compare how different choices affect accuracy and prefill time.

For each layer we transfer, we skip the 8B’s layer computation and put the mapped keys and values into its cache. But there is another piece to handle: if the 8B needs to compute a layer after a group of skipped layers, it also needs a hidden state to pass into that layer. We train a second map, Δ, to estimate how the skipped layers would have changed that hidden state.

We try different choices of layers to transfer. For each choice, we fit new initial maps and train them for 1,500 steps using the same KL-based method as Experiment 0.

Here’s what we see when we change which layers the 8B computes:

Keeping the first layers on the 8B improves GSM8K accuracy. The 8B processes its 36 layers in order, from first to last. In these runs, we let it compute the first layers and transfer the cache for the last layers:

First layers computed by the 8B Last layers transferred from 0.6B GSM8K accuracy (% of 8B with its own cache) Prefill speedup
6 30 69% 2.4×
15 21 76% 1.55×
18 18 88% 1.35×
21 15 94% 1.23×
24 12 97% 1.14×

When we reverse the split and transfer the first 18 layers instead, GSM8K accuracy falls to 13% of the 8B’s accuracy with its own cache.

  • Keeping 15–18 of the 36 layers on the 8B gives us a useful trade-off. We recover much of the GSM8K accuracy while still reducing prefill time. With fewer than about nine layers computed by the 8B, the tested plans stay close to the accuracy of transferring every layer, but add the cost of running those layers.
  • The layer we start with matters for the interleaved plans we tested. Transferring every other layer while letting the 8B compute layer 0 gives 87% of the 8B’s GSM8K accuracy at a 1.31× prefill speedup. Keeping every other layer but transferring layer 0 gives 59%. Layer 0 contains the attention sink, so sensitivity to errors there may be one reason for the gap.
  • The Δ map matters when we skip layers. Without it, the tested interleaved plans reach around 50% of the 8B’s score on each task. They perform worse than transferring every layer, at a similar prefill speed.

These timings come from Qwen3-0.6B → Qwen3-8B in Hugging Face. The small model and the mapper account for a sizeable part of the work in this pair. The trade-off could look different with a larger target model, where running each layer may cost more.

Experiment 3: letting the big model read the tail

In Experiment 2, letting the 8B compute more layers improved accuracy, but reduced the prefill speedup. Now we try a different split: the 0.6B reads most of the prompt, and the 8B reads the final part itself using the mapped cache for the earlier tokens. We call that final part the native tail.

In an earlier run, letting the 8B read the last 512 tokens reduced the average KL divergence between next-token distributions from 0.135 to 0.047. To see how this affects task scores and speed, we combine six layer plans from Experiment 2 with five tail sizes: none, 1/32, 1/16, 1/8, and 1/4 of the prompt. We evaluate each combination on the same 300 SQuAD, 300 HotpotQA, and 400 GSM8K questions.

We express the tail as a fraction so it scales with the length of each prompt. We use the existing Experiment 2 mappers without retraining them; the 8B reads the tail at inference time.

Here’s what we see when we vary the layers and the tail:

  • A short tail improves GSM8K accuracy in this setup. With every layer transferred and no tail, the 8B reaches 70% of its own GSM8K accuracy. Letting it read the last 1/16 of the prompt raises that to 96%, with a 2.5× prefill speedup at 8k tokens. The layer-only plan with similar accuracy, last:12, gives a 1.12× speedup. Here, the math question is near the end of the transferred prompt: its median length is 5.3% of the prompt. A 1/16 tail covers the whole question in two thirds of the prompts. A 1/32 tail covers the whole question in only 6% of prompts, but still raises accuracy to 87% of the 8B’s.
  • The tail does not improve the all-transferred HotpotQA result. It stays at 74% of the 8B’s score across the tail sizes. The 8B already reads the question header in this setup, while the documents remain transferred. Letting the 8B compute more layers raises the score to 89% with last:12; adding a tail raises it to as much as 94%.
  • SQuAD changes little across the combinations. Scores stay between 91% and 95% of the 8B’s score.
  • The cost of the tail depends on context length. With every layer transferred and a 1/4 tail, prefill is 1.75× faster at 8k tokens and 1.40× faster at 32k. At 2k tokens, the tested tails bring speedup down to 0.8–1.0×. Our implementation processes the tail in a second forward pass, which adds fixed overhead; a serving implementation could potentially reduce that overhead.

For these prompts, letting the 8B read the final part helps most when it contains information the 8B needs to handle directly, as with the GSM8K questions. For HotpotQA, where the relevant information is spread across the transferred documents, computing more layers is more useful in this experiment.

Experiment 4: a hybrid big model (Qwen3.5-4B → Qwen3.8-27B)

So far, we have used two Qwen3 models with attention layers throughout. Now we move to the pair from the OneTriangle post: Qwen3.5-4B and Qwen3.8-27B. Both are hybrid models: three out of every four layers use Gated DeltaNet, while the remaining layers use full attention.

The full-attention layers keep keys and values for each prefix token, which we can map as before. DeltaNet layers need a different approach. Instead of keeping a per-token KV cache, each layer maintains two fixed-size states:

  • A recurrent state, which the layer updates as it processes tokens and uses when processing the next token.
  • A convolution state, which holds the recent inputs needed by the layer’s short causal convolution.

These states do not grow with the length of the prefix. During decoding, the layer continues updating them as it processes new tokens.

Building the DeltaNet states

Rather than predict these states directly, we map the 4B’s hidden states to an estimate of the input to each 27B DeltaNet layer. We then use the 27B’s own DeltaNet computation to build the states from that estimated input. The diagram follows this path for one layer; the Algorithm and Code tabs show the steps in more detail.

Next, we compare task scores for the 27B using its own cache, the 27B using the transferred cache, and the 4B answering on its own:

method SQuAD F1 HotpotQA F1 GSM8K
Qwen3.8-27B itself 0.929 0.775 0.907
Qwen3.5-4B prefill → transfer 0.797 (86%) 0.717 (93%) 0.868 (96%)
Qwen3.5-4B alone 0.897 (97%) 0.720 (93%) 0.855 (94%)
27B, closed book 0.301 0.329 –

On these QA tasks, the 4B answering on its own scores about as well as or better than the 27B using the transferred cache. On GSM8K, transfer scores 0.868 against the 4B’s 0.855. To see whether the larger model offers more of an advantage on longer contexts, we turn to long-context evaluation next.

Experiment 5: long-context prefill, 8k to 248k tokens

The short-context results left me with another question: would transfer be more useful when the prompt gets really long? Long contexts are also where saving prefill time could matter most. I wanted to see how much time transfer saves as the prompt grows, and whether it still works beyond the mapper’s training length of at most 2k tokens.

I built a dedicated benchmark (make_long_data.py) with two parts:

  • Needle in a haystack: 20 prompts at each of 8k, 16k, 32k, 64k, 128k and 248k tokens, each with 4 keys to retrieve. This checks retrieval.
  • LongBench v2: 100 questions of up to 120k tokens, sampled with seed 0. These are 4-way multiple-choice questions that need reasoning over the whole document, so they actually separate strong models from weak ones.

For timing I measured two things. The first is the full transfer pipeline in HuggingFace, end to end. The second is native time to first token in SGLang for both models. SGLang has no transfer path yet, so its 27B ÷ 4B ratio is the ceiling an optimised implementation could approach.

Most of the gap between the measured 2.2–2.4× and the 4–6× ceiling is the DeltaNet state fill. The 27B still runs its 48 DeltaNet kernels over the full prompt, just without their outputs. That is why the transfer pipeline costs about 1.75× the 4B prefill alone (8.4 s vs 4.8 s at 128k).

Now let’s compare answer quality. For LongBench v2, we report the fraction of 100 questions answered correctly. For the needle test, we report retrieval accuracy across prompts from 8k to 248k tokens, with 20 prompts at each length.

Prompt processing Answering model LongBench v2 accuracy Needle retrieval accuracy
Qwen3.8-27B Qwen3.8-27B 52% 100%
Qwen3.5-4B, with its cache mapped to the 27B Qwen3.8-27B 50% 100% at every length
Qwen3.5-4B Qwen3.5-4B 39% 100%

The LongBench v2 results show the clearest difference between the three setups. The 27B answers 52 of the 100 questions correctly when it reads the prompt itself, and 50 when it uses the transferred cache. The 4B answering on its own gets 39. With only 100 questions, we should be cautious about drawing conclusions from the small gap between the two 27B runs.

On the needle test, the 27B retrieves every needle using the transferred cache, including at 248k tokens. That is well beyond the mapper’s training prefixes of at most 2k tokens. But the 4B answering on its own also retrieves every needle, so this test does not show whether transfer improves retrieval. The LongBench length breakdown gives us a more useful next step: train the mapper on longer prefixes and test whether that improves the results beyond 64k tokens.

Experiment 6: dense → MoE (Qwen3.5-4B → Qwen3.5-35B-A3B)

The hybrid model worked, so I wanted to see if transfer would also work when the larger model was a mixture of experts (MoE). I tried transferring from a dense model to an MoE. The same recipe worked here too: KL dropped from 0.175 to 0.066 after training, top-1 agreement reached 0.889, and task scores were the best of any pair I tried:

method SQuAD F1 HotpotQA F1 GSM8K
Qwen3.5-35B-A3B itself 0.918 0.747 0.922
Qwen3.5-4B prefill → transfer 0.906 (98.7%) 0.705 (94.5%) 0.838 (90.8%)
Qwen3.5-4B alone 0.897 0.720 0.855

But for this pair, transfer does not help much with speed. The MoE activates about 3B parameters per token, fewer than the dense 4B that would replace it in prefill. At 8k tokens the 35B-A3B prefills in 0.23 s and the 4B in 0.18 s. Once the maps and the DeltaNet fill are added, transfer is 0.88–1.03× the native speed: slower at every length except 2k. This is a feasibility result: the cache of a sparse model can be predicted from a dense one. For speed, you would pair a much larger MoE with a much smaller prefiller.

I also tried google/gemma-4-E4B → gemma-4-26B-A4B, and it is blocked by a library bug. In transformers 5.23, Gemma-4’s cached decoding path disagrees with its own full forward pass (KL 0.10 on a continuation even with the exact cache), so any transfer number would measure the bug, not the mapper. I stopped there and kept a small script that reproduces the mismatch.

Experiment 7: across model families and tokenizers

So far, we have transferred between models in the same family. Now we try two cross-family pairs: Qwen3-4B → Gemma3-12B and Gemma3-4B → Qwen3-14B.

These pairs introduce a new challenge. Qwen3 and Gemma3 use different tokenizers, so they can split the same text into different tokens. To build the larger model’s cache, we need to decide which small-model position supplies the information for each large-model token.

We align the tokens by character position. For each large-model token, we select the small-model token that contains its last character. We also make three changes to the mapper setup:

  • We add the large model’s token embedding as an input to the mapper. This only requires an embedding lookup.
  • We let the large model prefill the <bos> token and use its own keys and values for that attention sink.
  • We match source layers to target layers by their relative depth in each model.

The results are mixed:

In the Qwen → Gemma direction, the translated cache demonstrably carries the document: QA scores sit far above closed book. But Qwen3-4B on its own already scores 0.738 on this SQuAD setup, so the transfer is worse than not transferring at all. The Gemma → Qwen direction mostly fails: HotpotQA lands below closed book, which means the cache actively misleads the decoder. A curiosity: that direction reaches the better fidelity KL (0.135) and the worse task scores. Matching the next-token distribution on web text is not the same as preserving what a QA prompt needs.

Learnings:

  • Partial-layer transfer trades speed for accuracy. Letting the larger model compute its first layers can recover accuracy while still reducing prefill time.
  • Long contexts make a stronger case for transfer. The larger model using a transferred cache performs close to its own-cache baseline on LongBench v2.
  • Hybrid models need a different approach. Mapping DeltaNet inputs lets the larger model build its recurrent and convolution states, but that computation adds cost.
  • The prefiller’s compute matters for MoE models. A smaller dense model does not necessarily prefill faster than a larger sparse model.
  • Cross-family transfer needs more work. Token alignment carries information across model families, but the tested transfers do not beat the small model answering on its own.
